Журнал того, что нашлось при переносе **genorg.ru** с боевой PHP-CMS
на Next.js + Strapi, и что с этим сделано. Документ исторический:
описание замеров и решений на тот момент. Текущее состояние проекта —
в [README.md](../README.md).

Ниже — исходный README проекта на момент переноса.

> **Важно.** Описанный здесь mock-режим, локальный редактор `/admin`,
> `CMS_PROVIDER` и `ADMIN_TOKEN` **удалены из проекта**. Контент и фото
> живут только в Strapi; `/admin` теперь редирект в админку CMS, а при

> разделы — снимок прошлого состояния, не руководство к действию.

# Вариант C1 — Next.js (App Router) + headless CMS

Прототип варианта C1 для **genorg.ru** (ДИЭН-Системс, аренда ДГУ).
Это не «макет страницы», а **рабочее приложение**: 100 статически
собранных страниц, реальные данные боевого сайта, headless-слой,
который переключается одной переменной окружения.

### Ключевое решение: один catch-all вместо 91 маршрута

Боевой сайт использует **плоские односегментные адреса**
(`/arendadizelnogogeneratora100kvt`, `/arendapes60kvt`,
`/kompressornasmeny330`). В App Router плоский URL на верхнем уровне
возможен только через catch-all — поэтому вся маршрутизация живёт
в `app/[...slug]/page.tsx`, а тип контента определяется по данным CMS.

**Меняем движок, не меняем адреса** → 301-редиректов почти не нужно,
риск падения позиций ≈ 0.

Страницы живут в ISR (revalidate = 60 с), а `dynamicParams` не ограничен:
запись, добавленная в CMS после сборки, рендерится по первому запросу
и дальше кэшируется. Публикация новой позиции, статьи или редиректа
работает без `next build` — раньше (`dynamicParams = false`) такая запись
до пересборки отдавала 404, хотя уже попадала в sitemap.

## 3. Модель данных: 6 легаси-шаблонов → 5 сущностей

Боевая CMS (PHP) использовала отдельный шаблон для каждой категории:
ДГУ, ПЭС, компрессоры, компрессоры на смену, манипуляторы, продажа б/у.
В headless это **одна сущность** `equipment` с дискриминатором `category`:

```ts
interface Equipment {
  slug: string;            // legacy-URL без ведущего слэша
  category: 'generator' | 'pes' | 'compressor'
          | 'compressor-shift' | 'manipulator' | 'used';
  title: string;
  model: string;           // Airman SDG150 / HINO 500 / …
  power: number | null;    // кВт / т / бар
  powerUnit: string;
  price: { value: number; unit: string } | null;   // 2000 ₽ /сутки
  specGroups: { group: string; rows: { label: string; value: string }[] }[];
  description: string;
  legacyUrls: string[];    // источник 301-редиректов
}
```

Следствие: **добавление новой категории = одна запись в CMS**, а не
новый шаблон на фронте.

## 4. Админка

### Главное: CMS поднята, менеджеры — с обычным логином

**http://127.0.0.1:1337/admin** — настоящая админка Strapi 5.62 с обычной страницей
входа (email + пароль), ролями и историей изменений. Никаких `ADMIN_TOKEN` на
стороне сайта больше не нужно.

Вход: обычная форма. Пароль меняется в **Settings → Users → [пользователь] →
Reset password**. Добавить менеджера: **Settings → Users → Create new user**,
выбрать роль. Роли настраиваются в **Settings → Roles**.

Язык интерфейса панели переключается там же: **Settings → Global settings →
Interface language → Русский**. (Программно локаль лежит в колонке
`admin_users.locale` — см. `scripts/set-admin-locale.mjs`.)

### Локальный редактор `/admin` (mock-режим)

В корне сайта есть служебная страница `/admin` и `POST /api/admin` —
правка `content/seed.json` без CMS, только для локальной разработки
и mock-стендов. Правила доступа:

* без `ADMIN_TOKEN` в окружении запись запрещена полностью;
* известный дефолт `genorg-local-admin` в production-сборке
  отклоняется — защита от «скопировал `.env.example` как есть»
  (сам дефолт из примера убран);
* в production-сборке (`next build && next start`) редактор отключён,
  пока не задано `ALLOW_MOCK_ADMIN=1`. Прод-редакция контента —
  только через Strapi.

### Как это устроено

```
Strapi 5.62 (Node, SQLite)                 Next.js 15 (App Router)
┌───────────────────────────┐             ┌──────────────────────────┐
│ Content Manager (React)   │             │ 92 страницы SSG/ISR      │
│ /admin/auth/login         │             │ lib/cms.ts               │
│ Роли, история, медиа     │             │  ├ mock  → seed.json     │
└─────────┬─────────────────┘             │  └ strapi→ REST /api     │
          │ REST /api + токен               └──────────────────────────┘
          ▼
   content/seed.json  ←── migrate-to-cms.mjs (обход боевого сайта)
          │
          └──────────────► import-to-strapi.mjs
```

Фронт **не знает**, откуда пришли данные: `lib/cms.ts` возвращает одинаковые
объекты из `seed.json` (mock) или из REST API Strapi. Переключение — переменная
окружения `CMS_PROVIDER`.

Все методы провайдера обёрнуты в React `cache()`: один рендер страницы
(layout + generateMetadata + сам компонент) ходит в CMS один раз, а не 2–4.
TTL fetch'ей к Strapi (60 с) согласован с revalidate страниц — правка цены
в CMS доезжает до сайта не дольше минуты.

HTML-поля из CMS (`bodyHtml`) перед рендером проходят allowlist-санитизацию
(`lib/sanitize.ts`): остаются только разрешённые теги и атрибуты,
инлайн-обработчики и опасные схемы ссылок (`javascript:`, `data:`)
вырезаются. JSON-LD-блоки собираются через `jsonLd()` (`lib/seo.ts`) —
эскейп «<» не даёт строке из поля CMS закрыть тег `<script>` раньше времени.

## 4a. Docker и Postgres: что реально удалось

| Шаг | Статус |
|---|---|
| Docker Desktop 4.x установлен | ✅ (CLI 29.9.3) |
| Служба `com.docker.service` | ✅ Running |
| WSL2 | ❌ не установлен (`wsl --install` требует перезагрузки) |
| **Виртуализация в BIOS** | ❌ **`VirtualizationFirmwareEnabled = False`** |

**Docker не запустится**, пока в UEFI не будет включён Intel VT-x / AMD-V —
это настройка прошивки, её нельзя включить из Windows. Дальше: `wsl --install`
→ перезагрузка → Docker поднимется.

Обойти это нельзя, но и **не нужно**: Strapi полностью работоспособен на SQLite
(файл `cms-admin/.tmp/data.db`), а весь стенд уже поднят. Docker нужен только
для Postgres — а он в данном проекте не является обязательным: 47 позиций,
19 статей и 13 страниц SQLite обслуживают без нагрузки.

Когда виртуализация будет включена:

```powershell
cd cms
docker compose up -d          # Strapi :1337 + Postgres :5432
```

Файлы уже подготовлены: `cms/docker-compose.yml` и 8 схем контента
(`cms/schemas/*.json`). Для перехода на Postgres достаточно поменять
`DATABASE_CLIENT=postgres` в `cms-admin/.env` и выполнить миграцию.

## 7. Приём заявок

Клиентская форма шлёт JSON на `/api/leads` (Server Route Handler), который:

1. отбрасывает honeypot-заявки и ограничивает частоту: в форме есть
   скрытое поле `website` — человек его не видит и не заполняет,
   боты заполняют (такая заявка получает ответ «успех», но никуда
   не доставляется); сверх лимита `LEADS_RATE_LIMIT` (по умолчанию
   5 заявок в час с одного IP) эндпоинт отвечает 429;
2. валидирует вход (имя, телефон по regex);
3. **сохраняет заявку в CMS** — коллекция «Заявки» (`api::lead`).
   Это основное хранилище: менеджер видит заявки в админке
   (Content Manager → Заявки) и берёт их в работу;
4. проксирует на легаси-эндпоинт `/sendfeed/` — пока боевой сайт
   жив, заявки продолжают уходить в существующую почтовую цепочку
   без переделки бэкенда на этапе миграции;
5. дублирует заявку в CRM, если задан `CRM_WEBHOOK_URL`;
6. если CMS недоступна (режим `mock`) — пишет заявку в
   `data/leads.ndjson`, чтобы она точно не потерялась. В проде каталог
   `data/` смонтирован на хост и включён в ежедневный бэкап.

CORS на `/api/leads` по умолчанию выключен: заголовки выдаются только
при заданном `ALLOWED_ORIGIN` (форма на другом домене). Same-origin
форме они не нужны, а открытый «*» позволял бы посторонним сайтам
дёргать эндпоинт из браузера.

Клиент не знает ни про `/sendfeed/`, ни про CRM — форма не ломается
при смене бэкенда.

**Почему так.** До правки единственным каналом был боевой сайт.
Когда его отключат (а при переезде отключат обязательно), заявки
стали бы возвращать «Не удалось отправить заявку» и исчезать
безвозвратно. Теперь заявка гарантированно лежит в CMS, а письмо
и CRM — дополнительные каналы, а не единственные.

**Что настроить перед запуском**

| Переменная | Назначение |
|---|---|
| `STRAPI_WRITE_TOKEN` | токен API с правом записи — им сайт сохраняет заявки в CMS |
| `LEGACY_FEED_URL` | адрес боевого эндпоинта (по умолчанию `https://genorg.ru/sendfeed/`) |
| `CRM_WEBHOOK_URL` | если используется CRM |
| `LEADS_RATE_LIMIT` | лимит заявок в час с одного IP (по умолчанию 5) |
| `ALLOWED_ORIGIN` | CORS для `/api/leads` — только если форма на другом домене; по умолчанию заголовки не выдаются |
| `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` | план: уведомление менеджерам напрямую (в коде пока не используются) |

Уведомление на почту сейчас идёт через цепочку боевого сайта.
Когда он будет отключён — нужно подключить SMTP (Mail.ru, Яндекс.360)
и отправлять письмо из `/api/leads`; хранилище в CMS при этом
остаётся основным.

## 8. Что нашлось при миграции (и уже исправлено)

| Находка | Что сделано |

## 10. Известные ограничения прототипа

- `First Load JS` — **103 КБ** (runtime React + Next). Вариант B
  (статичный прототип без фреймворка) весит 9 КБ. Разница — цена
  headless-подхода; окупается она не скоростью, а управляемостью
  контента и возможностью добавить кабинет/оплату.
- **Гидратация.** HTML отдаётся готовым и рисуется мгновенно, но
  интерактив (калькулятор, форма, меню) оживает после загрузки JS.
  На медленной мобильной сети это 300–600 мс «мёртвого» клика.
  Если это критично — интерактив можно вынести в отдельные
  `<script>`-бандлы или перейти на вариант B. Замер: гидратация
  на прогретом соединении — мгновенно.
- **Картинки оптимизированы только для дизельных генераторов** (12 моделей).
  Для ПЭС, компрессоров и манипуляторов пока заглушка — нужно
  перекодировать исходники по тому же рецепту (`audit/optimize-images.js`).
- Текстовые блоки (преимущества, шаги, тарифы, FAQ, отзывы) лежат в
  `lib/content-blocks.ts`. В проде они переезжают в CMS как
  коллекция `content-blocks` — перенос механический.
- Отзывы и рейтинг 4,9 — в макете. Реальные цифры нужно подтвердить
  в Яндекс.Картах и вынести в CMS.

## 14. Отзывы и рейтинг с Яндекс.Карт

### Что сделано

| Было | Стало |
|---|---|
| Два выдуманных отзыва в коде | Реальные отзывы с Яндекс.Карт, 2 лучших |
| Захардкоженные «4,9» и «47 отзывов» | **Живой бейдж Яндекса** — всегда актуальные цифры |
| Фото не тянулись | Фото из отзывов — прямые ссылки на CDN Яндекса |

**Почему бейдж, а не числа.** Яндекс отдаёт агрегированную оценку
организации только через браузерную сессию — API отвечает пустым
токеном. Поэтому единственный честный способ показать реальную
оценку — встроить их собственный виджет
(`yandex.ru/sprav/widget/rating-badge/1088163471`). Он всегда показывает
актуальные данные, и мы ничего не выдумываем.

### Отзывы

`scripts/fetch-yandex-reviews.mjs` разбирает JSON-блок отзывов прямо в
HTML публичной страницы Яндекс.Карт (без API-ключа) и:

* сортирует — сначала по оценке (5 → 1), при равенстве по дате;
* отбрасывает отзывы самой компании и её сотрудников;
* берёт 2 лучших для витрины, все 11 хранит в `content/reviews.json`;
* сохраняет **прямые ссылки** на фотографии из отзывов.

Фотографии намеренно **не хранятся на нашем домене** — это чужие
снимки пользователей, лежащие на CDN Яндекса. Мы только ссылаемся.

Обновление: `node scripts/fetch-yandex-reviews.mjs && node scripts/import-to-strapi.mjs --reset`.

В `reviews.json` два среза: `reviews` — 2 витринных, `all` — все 11.
В mock-режиме (без CMS) фронт читает отзывы напрямую из
`content/reviews.json` (ключ `all`) — в `seed.json` поле отзывов пустое.

### 2. Фильтр по бренду давал пустую выдачу

**Причина.** Поле `brand` было в схеме, но не маппилось при импорте —

собирается из данных CMS и ведёт в ту категорию, где бренд есть.
Ссылка `/arendageneratorov?brand=Airman` → 9 карточек.

### 3. Хлебные крошки вели не в ту категорию

**Причина.** В Strapi категория хранится с полем `key`, а код искал
`c.id` — связь «позиция → категория» не работала, и все крошки
уезжали на `/arendageneratorov`.

**Что сделано.** Адаптер Strapi приводит `key` к `id`. Проверено на
всех шести категориях: компрессор → `/arendakompressorov`,
манипулятор → `/arendamanipulatora`, ПЭС → `/mobilnyegeneratory`,
компрессор на смену → `/kompressornasmeny`, б/у → `/prodazhabu`.

у всех 47 позиций** — по 3–4 группы, 12–17 строк.

## 18. Cookie-уведомление (152-ФЗ, ст. 18.1)

Оператор обязан получить согласие на обработку технических данных и
обеспечить возможность его отозвать.

**Как работает**

| Шаг | Что происходит |
|---|---|
| Первый визит | Показывается баннер: «Принять все» / «Только необходимые» |

### 14. Мобильное меню, липкая панель и подвал

**Мобильное меню не раскрывалось.** Причина оказалась не в `.hero__bg`,
а в шапке: у неё `backdrop-filter`, а такой элемент становится
containing block для `position: fixed`. Поэтому меню с
`position: fixed; inset: 0` растягивалось не на экран, а на высоту
шапки — 68 px, и список пунктов просто не помещался.

Решение: панель выносится в **портал на `<body>`** (`createPortal`).
За пределами шапки `fixed` считается от окна, панель занимает весь
экран и всегда лежит поверх сайта (`z-index: 200`).

**Липкая мобильная панель** (`mcta` — «Позвонить / Каталог /
Рассчитать») удалена целиком: заказ и так уводит на форму, а звонок
и каталог есть в шапке, меню и подвале.

**Подвал на узких экранах** — блоки «Услуги» и «Компания» стали
сворачиваемыми (`components/FooterList.tsx`): заголовок превращается
в кнопку со стрелкой, список свёрнут по умолчанию. На десктопе это
обычные списки. Блок «Контакты» остался раскрытым — он и есть главное.

## 22. Формулировки на страницах каталога

Тексты на страницах категорий собираются кодом в
`lib/category-content.ts` — из данных каталога, а не из legacy-описаний.
Правила, которые там зафиксированы:

| Что | Формулировка | Почему так |
|---|---|---|
| Количество в каталоге | «16 **видов** дизельных генераторов» | перечислены модели, а не единицы техники; «16 единиц в собственном парке» вводило в заблуждение |
| Единица цены | берётся из данных: `/сутки` или `/смена` | у ПЭС, манипуляторов и компрессоров на смену цена за смену 8 часов, у генераторов и компрессоров — за сутки |
| Состав аренды | «включены в стоимость*» + сноска «* В зависимости от тарифа» | состав зависит от тарифа (сухая аренда / с оператором и топливом) |
| Заголовок раздела | «Что входит в стоимость *» | та же сноска, что и в тексте |
| Шапка страницы | без legacy-описания | текст из CMS повторял «краткий ответ» ниже — дублирование убрано |
| Склонение | 1 вид / 2 вида / 5 видов, 2 единицы | `pluralize()` по числу моделей |

Единица цены **не** зашита в список категорий: она читается из поля
`price.unit` первой позиции с ценой. Если в CMS у ПЭС поменять
`/смена` на `/сутки`, текст обновится сам.

Отладочный скрипт для проверки формулировок:


Раньше тексты сайта жили в коде: `lib/content-blocks.ts` (тарифы, шаги,

Сейчас **источник правды — CMS**:

### Новые коллекции

| Коллекция | Что в ней | Примеры |
|---|---|---|
| **Текстовый блок** (`content-blocks`) | 27 блоков, по одному на смысловой экран | `home.hero`, `home.tariffs`, `header.main`, `footer.main`, `catalog.main`, `product.main`, `contacts.main`, `calc.main`, `form.main`, `cookie.main`, `errors.main`, `seo.main` |
| **Пункт меню** (`menu-items`) | 25 пунктов в четырёх группах | верхнее меню, список техники в мега-меню, колонки подвала |
| **Категория техники** — новые поля | краткий ответ, факты, состав аренды, FAQ | `answer`, `facts`, `includes`, `includesNote`, `faq`, `seoDescription` |
| **Настройки сайта** — новые поля | логотип, знак, фон, тексты подвала, SEO по умолчанию | `logo`, `logoMark`, `heroImage`, `footerAbout`, `footerBottom`, `seoTitle` |

### Как это работает

```
CMS (Strapi)                    content/cms-content.json
  │  текстовые блоки            │  снимок тех же текстов
  │  пункты меню                 │  (запасной вариант)
  │  медиатека                  │
  ▼                             ▼
lib/content.ts  ────►  Content  ──►  компоненты сайта
```

* `lib/content.ts` — доступ к блокам: `c.s('home.hero', 'eyebrow', tokens)`,
  `c.o('catalog.main', tokens)`, `c.a('home.faq', 'faq', tokens)`, `c.menu('header')`.
* Значения из CMS имеют приоритет. Если блок в CMS не заполнен —
  берётся значение из `content/cms-content.json` (тот же снимок, из
  которого CMS наполняется). Это страховка от пустой страницы, а не
  второй источник правды: `scripts/_check-cms-coverage.mjs` проверяет,
  что в CMS заполнено всё.
* `lib/tokens.ts` собирает числа из каталога и настроек: `{price}`,
  `{count}`, `{powerRange}`, `{discountPercent}`. В текстах CMS это
  шаблоны — редактор меняет формулировку, а цифры остаются живыми.

### Медиа

Фотографии лежат в медиатеке Strapi, а не в репозитории:

* `equipment.image` и `case.image` — поля типа **media** (были строки
  вида `eq/21`);
* `site-setting.logo`, `logoMark`, `heroImage` — тоже media;
* сайт отдаёт `<img srcset>` из оригинала и уменьшенных копий,
  которые Strapi создаёт при загрузке (`thumbnail/small/medium/large`);
* в `public/` остались только иконки приложения (`favicon.ico`,
  `icon.png`, `apple-icon.png`) — браузеры ждут их по фиксированным путям;
* исходники легаси-фото перенесены в `assets/legacy-images/` — это
  архив миграции, сайт их не раздаёт.

Ссылка на фото строится по публичному адресу CMS (`CMS_PUBLIC_URL`),
внутренний адрес контейнера (`http://strapi:1337`) браузеру не
доступен.

### Перенос

```
node scripts/import-content-to-cms.mjs              # тексты, меню, медиа
node scripts/import-content-to-cms.mjs --clean-media  # с чистой медиатеки
node scripts/import-body-images.mjs                  # фото внутри текстов
```

Скрипт идемпотентен: повторный прогон обновляет записи, а не создаёт
дубликаты. Файлы в медиатеке переиспользуются по имени.

Три фотографии, вшитые в тексты статей и страниц, перенесены отдельно:
оригиналы скачиваются с боевого сайта, заливаются в медиатеку, а в
тексте остаются относительные пути (`/uploads/body_0_….jpg`) — публичный
адрес CMS подставляет сайт при рендере (`lib/media.ts → withCmsMedia`).
Так текст не зависит от окружения: dev, стейдж или прод.

### Проверки

```
node scripts/_check-cms-coverage.mjs   # все ли тексты и фото в CMS
node scripts/_check-placeholders.mjs   # все ли шаблоны подставлены
node scripts/check-images.mjs          # доступны ли все картинки
```

## 25. Устойчивость к недоступной CMS

Если Strapi временно недоступна (перезапуск, миграция, обрыв сети),
сайт **не отдаёт 500**: адаптер `ResilientCMS` в `lib/cms.ts`
переключается на локальный снимок `content/seed.json` и
`content/cms-content.json` и пишет предупреждение в лог.

Именно поэтому в проекте остался запасной снимок контента: он нужен
не как второй источник правды, а чтобы страница пережила аварию CMS.

Проверено на практике: при упавшей CMS сборка проходит и отдаёт
100 страниц вместо 101 — тексты на месте, фотографий нет (они в CMS),
вместо битых картинок рисуются заглушки.

## 27. Сторож CMS (локальная разработка)

В режиме `develop` Strapi на этой машине периодически падает — сборка
в это время собирается на запасном снимке, а не на живых данных.
Сторож поднимает CMS и следит за ней:

```
node scripts/_watch-strapi.mjs
```

На сервере это не нужно: там Strapi работает в `production` под
systemd/docker и падать не должен.

## 28. Безопасность

Меры, которые закрывают типичные риски эксплуатации.

### Контент из CMS

* **Санитизация HTML.** Поля `bodyHtml` перед рендером проходят
  allowlist-фильтр (`lib/sanitize.ts`): остаются только разрешённые
  теги и атрибуты, инлайн-обработчики `on*` и опасные схемы ссылок
  (`javascript:`, `data:`, `vbscript:`) вырезаются. Разметка
  legacy-страниц (colspan/rowspan прайса, классы) сохраняется.
* **JSON-LD.** Блоки собираются через `jsonLd()` (`lib/seo.ts`) —
  эскейп `<` не даёт строке из поля CMS закрыть тег `<script>`.

### Приём заявок (`/api/leads`)

1. Honeypot: скрытое поле `website` — человек его не видит, боты
   заполняют; такая заявка получает ответ «успех», но никуда не
   уходит.
2. Rate limit: `LEADS_RATE_LIMIT` (по умолчанию 5) заявок в час с
   одного IP, сверх лимита — HTTP 429.
3. Валидация входа: имя и телефон по regex.
4. CORS: заголовки выдаются **только** если задан `ALLOWED_ORIGIN`.
   Не задан — заголовков нет вовсе.

### Сборка и деплой

* Токен сборки (`STRAPI_TOKEN`) передаётся в образ как BuildKit
  **secret** (`RUN --mount=type=secret`), а не как `ARG`: аргументы
  сборки сохраняются в истории образа, секрет — нет. Файл
  `secrets/strapi_token.txt` создаёт `deploy.sh` из `.env` и он
  в `.gitignore`.
* Мок-редактор `/admin` в production-сборке отключён
  (`ALLOW_MOCK_ADMIN=1` включает), дефолтный `ADMIN_TOKEN`
  отклоняется в production. Прод-правка — только через Strapi.

### Секреты в репозитории

* Пароли и токены не хранятся в коде: `create-managers.mjs` берёт их
  из переменных окружения, а `_save-credentials.mjs` — из `.env`.
* `.env`, `.env.local`, `.env.production`, `.strapi-tokens.json`,
  `secrets/`, `data/` — в `.gitignore`.
* Перед отправкой в GitHub проверяется индекс:

```
node scripts/_check-secrets.mjs
```

  Скрипт ищет в отслеживаемых файлах мусор (логи, кэш, сборка,
  медиатека) и типичные секреты — пароли, ключи, токены GitHub и
  действующие API-токены Strapi.
